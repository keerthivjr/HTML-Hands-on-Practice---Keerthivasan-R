SOLID & Design Patterns in C#

Fresher's practical guide — ready-to-run examples with real-world context

SOLID Principles + Design Patterns

These are the foundation every professional C# developer must master. SOLID keeps your code clean; Design Patterns solve recurring architectural problems.

SOLID Principles
S
Single Responsibility
A class should have only ONE reason to change. One job, done well.
O
Open / Closed
Open for extension, closed for modification. Add features without breaking existing code.
L
Liskov Substitution
Subtypes must be substitutable for their base types without altering correctness.
I
Interface Segregation
Clients should not be forced to implement interfaces they don't use.
D
Dependency Inversion
Depend on abstractions (interfaces), not concrete implementations.
Design Patterns
①
Singleton Pattern
Ensure only one instance of a class exists — e.g. config manager, logger.
🏭
Factory Pattern
Create objects without specifying the exact class — decouple creation from usage.
👁
Observer Pattern
Subscribe to events and get notified when state changes — event-driven systems.
🗄
Repository Pattern
Abstract data access behind an interface — swap DB without touching business logic.
Start with the tabs above, reading EACH principle/pattern's BAD example first, then the GOOD refactor. The "why" sticks better when you feel the pain of the bad code first.
S — SRP

Single Responsibility Principle

A class should have one and only one reason to change. If a class handles multiple responsibilities, changing one can unexpectedly break others.

Rule: Every class/method should do one thing and do it well. Split classes that grow too fat.
BAD — One class doing too much
public class Employee
{
    public string Name { get; set; }
    public decimal Salary { get; set; }

    // ❌ Responsibility 1: Business logic
    public decimal CalculateTax()
    {
        return Salary * 0.2m;
    }

    // ❌ Responsibility 2: Database access
    public void SaveToDatabase()
    {
        // SQL INSERT logic here — belongs in a repository!
        Console.WriteLine($"INSERT INTO Employees VALUES ('{Name}', {Salary})");
    }

    // ❌ Responsibility 3: Reporting / formatting
    public void GeneratePaySlip()
    {
        Console.WriteLine($"--- Pay Slip for {Name} ---");
        Console.WriteLine($"Net: {Salary - CalculateTax()}");
    }
}
Refactor to GOOD
GOOD — Each class has ONE job
// 1️⃣ Pure data model
public class Employee
{
    public string Name { get; set; }
    public decimal Salary { get; set; }
}

// 2️⃣ Business logic only
public class TaxCalculator
{
    public decimal Calculate(Employee emp) => emp.Salary * 0.2m;
}

// 3️⃣ Data persistence only
public class EmployeeRepository
{
    public void Save(Employee emp)
        => Console.WriteLine($"Saving {emp.Name} to DB...");
}

// 4️⃣ Presentation / reporting only
public class PaySlipGenerator
{
    private readonly TaxCalculator _tax = new();

    public void Print(Employee emp)
    {
        var net = emp.Salary - _tax.Calculate(emp);
        Console.WriteLine($"--- Pay Slip for {emp.Name} ---");
        Console.WriteLine($"Gross: {emp.Salary:C} | Tax: {_tax.Calculate(emp):C} | Net: {net:C}");
    }
}

// ✅ Usage — clean orchestration
var emp  = new Employee { Name = "Priya", Salary = 50000m };
var repo = new EmployeeRepository();
var slip = new PaySlipGenerator();

repo.Save(emp);
slip.Print(emp);
Reason to change

Employee: only if data fields change

Reason to change

TaxCalculator: only if tax rules change

Reason to change

EmployeeRepository: only if DB changes

Reason to change

PaySlipGenerator: only if format changes

Easier to test Changes are isolated Smaller, focused classes Better reusability
Memory trick: If you describe a class and use "AND", it's doing too much. "Employee saves data AND calculates tax AND prints slips" → split it!
O — OCP

Open / Closed Principle

Software entities should be open for extension but closed for modification. Add new behavior by adding new code, not editing existing code.

Rule: Never modify a working class to add new behavior. Instead, extend it via inheritance or interfaces.
BAD — Every new shape breaks existing code
public class AreaCalculator
{
    // ❌ Every new shape requires modifying THIS method
    public double Calculate(object shape)
    {
        if (shape is Circle c)
            return Math.PI * c.Radius * c.Radius;
        else if (shape is Rectangle r)
            return r.Width * r.Height;
        // Adding Triangle means editing here — risky!
        throw new NotSupportedException("Unknown shape");
    }
}

public class Circle    { public double Radius { get; set; } }
public class Rectangle { public double Width, Height; }
GOOD — Add new shapes without touching AreaCalculator
// ✅ Abstraction — the contract every shape must fulfill
public interface IShape
{
    double Area();
}

// Each shape owns its own area formula
public class Circle : IShape
{
    public double Radius { get; set; }
    public double Area() => Math.PI * Radius * Radius;
}

public class Rectangle : IShape
{
    public double Width { get; set; }
    public double Height { get; set; }
    public double Area() => Width * Height;
}

// ➕ New shape added — AreaCalculator NOT touched!
public class Triangle : IShape
{
    public double Base { get; set; }
    public double Height { get; set; }
    public double Area() => 0.5 * Base * Height;
}

// ✅ Calculator is CLOSED for modification, open for extension
public class AreaCalculator
{
    public double TotalArea(IEnumerable<IShape> shapes)
        => shapes.Sum(s => s.Area());
}

// ✅ Usage
var shapes = new List<IShape>
{
    new Circle    { Radius = 5 },
    new Rectangle { Width = 4, Height = 6 },
    new Triangle  { Base = 3, Height = 8 }
};

var calc = new AreaCalculator();
Console.WriteLine($"Total Area: {calc.TotalArea(shapes):F2}");
// Output: Total Area: 102.54
Safe to extend No regression risk Polymorphism-driven
Key tool: interfaces and abstract classes. When you find yourself writing if/switch on types, that's your signal to apply OCP.
L — LSP

Liskov Substitution Principle

Objects of a subclass should be able to replace objects of the parent class without breaking the program. Subtypes must honor the parent's contract.

Rule: If S extends B, anywhere you use B you must be able to use S without unexpected behavior or exceptions.
BAD — Square "lies" about being a Rectangle
public class Rectangle
{
    public virtual double Width  { get; set; }
    public virtual double Height { get; set; }
    public double Area() => Width * Height;
}

// ❌ Square overrides both setters — breaks Rectangle's behavior
public class Square : Rectangle
{
    public override double Width
    {
        set { base.Width = value; base.Height = value; }
    }
    public override double Height
    {
        set { base.Width = value; base.Height = value; }
    }
}

// 💥 This works fine for Rectangle but BREAKS for Square!
void Resize(Rectangle r)
{
    r.Width  = 4;
    r.Height = 5;
    // Expected: 20, Actual for Square: 25 — LSP violated!
    Console.WriteLine(r.Area());
}
GOOD — Use a common abstraction, no forced inheritance
// ✅ Both implement the same interface — no faulty inheritance
public interface IShape
{
    double Area();
}

public class Rectangle : IShape
{
    public double Width  { get; }
    public double Height { get; }
    public Rectangle(double w, double h) { Width = w; Height = h; }
    public double Area() => Width * Height;
}

public class Square : IShape
{
    public double Side { get; }
    public Square(double s) { Side = s; }
    public double Area() => Side * Side;
}

// ✅ Works correctly for ALL shapes — LSP satisfied
void PrintArea(IShape shape)
    => Console.WriteLine($"Area: {shape.Area():F2}");

PrintArea(new Rectangle(4, 5)); // Area: 20.00
PrintArea(new Square(5));      // Area: 25.00
Predictable substitution No surprise exceptions Correct polymorphism
Test: Can you swap a subclass in EVERY place the base is used without changing behavior? If no → LSP violated. Prefer composition over inheritance when in doubt.
I — ISP

Interface Segregation Principle

No client should be forced to implement interfaces it doesn't use. Prefer many small, specific interfaces over one large, fat interface.

Rule: Split large interfaces into smaller ones. Implement only what you actually need.
BAD — One fat interface forces useless implementations
// ❌ "God interface" — forces all implementors to have ALL methods
public interface IWorker
{
    void Work();
    void Eat();
    void Sleep();
    void AttendMeeting();
}

// ❌ RobotWorker forced to implement Eat/Sleep — makes no sense!
public class RobotWorker : IWorker
{
    public void Work() => Console.WriteLine("Robot working...");
    public void Eat()  => throw new NotImplementedException(); // 💥
    public void Sleep() => throw new NotImplementedException(); // 💥
    public void AttendMeeting() => Console.WriteLine("Beep boop...");
}
GOOD — Small, focused interfaces
// ✅ Segregated interfaces — each does one thing
public interface IWorkable    { void Work(); }
public interface IEatable     { void Eat();  }
public interface ISleepable   { void Sleep(); }
public interface IMeetable    { void AttendMeeting(); }

// Human implements ALL (it can do all these things)
public class HumanWorker : IWorkable, IEatable, ISleepable, IMeetable
{
    public void Work()          => Console.WriteLine("Human working");
    public void Eat()           => Console.WriteLine("Human eating");
    public void Sleep()         => Console.WriteLine("Human sleeping");
    public void AttendMeeting() => Console.WriteLine("Human in meeting");
}

// ✅ Robot only implements what it actually does — clean!
public class RobotWorker : IWorkable, IMeetable
{
    public void Work()          => Console.WriteLine("Robot working");
    public void AttendMeeting() => Console.WriteLine("Robot attending meeting");
}

// ✅ Usage — polymorphic, clean
var workers = new List<IWorkable> { new HumanWorker(), new RobotWorker() };
workers.ForEach(w => w.Work());
No forced stubs Focused dependencies Easier mocking in tests
Watch for the smell: throw new NotImplementedException() in an interface method — that's ISP violated. Time to split!
D — DIP

Dependency Inversion Principle

High-level modules should not depend on low-level modules. Both should depend on abstractions. Details should depend on abstractions, not the other way around.

Rule: Inject interfaces/abstractions — never new up concrete classes inside high-level classes. This enables easy swapping and testing.
BAD — High-level class tightly coupled to low-level
// ❌ OrderService creates its own EmailNotifier — tightly coupled
public class EmailNotifier
{
    public void Notify(string msg)
        => Console.WriteLine($"[EMAIL] {msg}");
}

public class OrderService
{
    // ❌ Hard-coded dependency — can't swap to SMS without editing here
    private readonly EmailNotifier _notifier = new EmailNotifier();

    public void PlaceOrder(string product)
    {
        Console.WriteLine($"Order placed: {product}");
        _notifier.Notify($"Your order for {product} is confirmed!");
    }
}
GOOD — Depend on abstraction, inject the detail
// ✅ Abstraction — the contract
public interface INotifier
{
    void Notify(string message);
}

// Low-level implementations
public class EmailNotifier : INotifier
{
    public void Notify(string msg)
        => Console.WriteLine($"[EMAIL] {msg}");
}

public class SmsNotifier : INotifier
{
    public void Notify(string msg)
        => Console.WriteLine($"[SMS] {msg}");
}

// ✅ High-level class depends on ABSTRACTION, not concrete class
public class OrderService
{
    private readonly INotifier _notifier;

    // ✅ Dependency injected via constructor
    public OrderService(INotifier notifier) => _notifier = notifier;

    public void PlaceOrder(string product)
    {
        Console.WriteLine($"Order placed: {product}");
        _notifier.Notify($"Your order for {product} is confirmed!");
    }
}

// ✅ Swap notifier without changing OrderService at all!
var emailService = new OrderService(new EmailNotifier());
emailService.PlaceOrder("Laptop");
// [EMAIL] Your order for Laptop is confirmed!

var smsService = new OrderService(new SmsNotifier());
smsService.PlaceOrder("Phone");
// [SMS] Your order for Phone is confirmed!
Easily testable Swap implementations freely Foundation of DI containers
This is the foundation of ASP.NET Core's built-in Dependency Injection. Every time you see services.AddScoped<IRepo, SqlRepo>(), that's DIP in action.
Creational Pattern

Singleton Pattern

Ensures a class has only one instance throughout the application lifecycle, and provides a global access point to it.

Use when: You need exactly one shared resource — a logger, config manager, connection pool, or cache. Don't overuse — it can hide dependencies.
Thread-safe Singleton with Lazy<T> — recommended C# way
public sealed class AppLogger
{
    // ✅ Lazy ensures thread-safe single creation
    private static readonly Lazy<AppLogger> _instance
        = new(()  => new AppLogger());

    // ✅ Private constructor — no one can do: new AppLogger()
    private AppLogger()
    {
        Console.WriteLine("🔧 AppLogger initialized (happens ONCE)");
    }

    // ✅ Global access point
    public static AppLogger Instance => _instance.Value;

    private int _logCount = 0;

    public void Log(string message)
    {
        _logCount++;
        Console.WriteLine($"[LOG #{_logCount}] {DateTime.Now:HH:mm:ss} — {message}");
    }

    public int TotalLogs => _logCount;
}

// ✅ Usage — both variables point to the SAME instance
var logger1 = AppLogger.Instance;
var logger2 = AppLogger.Instance;

logger1.Log("Application started");
logger2.Log("User logged in");
logger1.Log("Order created");

Console.WriteLine($"Same instance? {ReferenceEquals(logger1, logger2)}");
Console.WriteLine($"Total logs: {AppLogger.Instance.TotalLogs}");

/* Output:
   🔧 AppLogger initialized (happens ONCE)
   [LOG #1] 10:30:01 — Application started
   [LOG #2] 10:30:01 — User logged in
   [LOG #3] 10:30:01 — Order created
   Same instance? True
   Total logs: 3
*/
Step 1

Private constructor prevents external instantiation

Step 2

Lazy<T> handles thread-safe first-time creation

Step 3

Static Instance property gives global access

Step 4

sealed prevents subclassing that could break the pattern

Thread-safe Single shared state Lazy initialization
In ASP.NET Core, register as services.AddSingleton<ILogger, AppLogger>() instead of hand-rolling Singleton — the DI container manages the lifetime for you.
Creational Pattern

Factory Pattern

Define an interface for creating objects, but let subclasses or a factory method decide which class to instantiate. Decouples object creation from usage.

Use when: The exact type to create depends on runtime conditions, or when you want to centralize and simplify complex object construction.
Factory Method Pattern — payment gateway example
// ✅ Common interface all payment providers must implement
public interface IPaymentProcessor
{
    void ProcessPayment(decimal amount);
    string ProviderName { get; }
}

// Concrete implementations
public class StripeProcessor : IPaymentProcessor
{
    public string ProviderName => "Stripe";
    public void ProcessPayment(decimal amount)
        => Console.WriteLine($"[Stripe] 💳 Processing ₹{amount:N0} via Stripe API...");
}

public class RazorpayProcessor : IPaymentProcessor
{
    public string ProviderName => "Razorpay";
    public void ProcessPayment(decimal amount)
        => Console.WriteLine($"[Razorpay] 🔐 Processing ₹{amount:N0} via Razorpay...");
}

public class UpiProcessor : IPaymentProcessor
{
    public string ProviderName => "UPI";
    public void ProcessPayment(decimal amount)
        => Console.WriteLine($"[UPI] 📱 Processing ₹{amount:N0} via UPI...");
}

// ✅ Factory — centralizes creation logic
public static class PaymentProcessorFactory
{
    public static IPaymentProcessor Create(string provider)
        => provider.ToLower() switch
        {
            "stripe"    => new StripeProcessor(),
            "razorpay"  => new RazorpayProcessor(),
            "upi"       => new UpiProcessor(),
            _           => throw new ArgumentException($"Unknown provider: {provider}")
        };
}

// ✅ Client code — never uses 'new' on concrete types
string[] providers = { "stripe", "razorpay", "upi" };
foreach (var p in providers)
{
    IPaymentProcessor processor = PaymentProcessorFactory.Create(p);
    Console.WriteLine($"\nUsing: {processor.ProviderName}");
    processor.ProcessPayment(5000);
}

/* Output:
   Using: Stripe
   [Stripe] 💳 Processing ₹5,000 via Stripe API...
   Using: Razorpay
   [Razorpay] 🔐 Processing ₹5,000 via Razorpay...
   Using: UPI
   [UPI] 📱 Processing ₹5,000 via UPI...
*/
Decoupling

Client uses IPaymentProcessor, never concrete classes

Extensibility

Add PayPal? Create class + add one line to Factory

OCP Bonus

Client code never changes when new providers are added

Testability

Inject a MockProcessor in tests — no real API calls

Centralized creation Decoupled from concretions Easy to extend
Factory + DIP is a power combo. The Factory creates objects, DIP injects the interface — your business logic never touches new ConcreteClass().
Behavioral Pattern

Observer Pattern

Defines a one-to-many dependency between objects. When one object (Subject) changes state, all its dependents (Observers) are notified automatically.

Use when: Multiple objects need to react to state changes — stock price alerts, event systems, UI data binding, notification systems.
Observer Pattern — stock price alert system
// ✅ Observer interface — all listeners must implement this
public interface IStockObserver
{
    void Update(string symbol, decimal price);
}

// ✅ Subject interface — defines subscription management
public interface IStockSubject
{
    void Subscribe(IStockObserver observer);
    void Unsubscribe(IStockObserver observer);
    void Notify();
}

// ✅ Concrete Subject — holds state and manages observers
public class StockMarket : IStockSubject
{
    private readonly List<IStockObserver> _observers = new();
    private string _symbol;
    private decimal _price;

    public void Subscribe(IStockObserver o)   => _observers.Add(o);
    public void Unsubscribe(IStockObserver o) => _observers.Remove(o);

    public void Notify()
        => _observers.ForEach(o => o.Update(_symbol, _price));

    // Triggers notification whenever price changes
    public void SetPrice(string symbol, decimal price)
    {
        _symbol = symbol; _price = price;
        Console.WriteLine($"\n📈 {symbol} price updated: ₹{price:N0}");
        Notify();
    }
}

// ✅ Concrete Observers — each reacts differently
public class MobileAlertObserver : IStockObserver
{
    private readonly string _user;
    private readonly decimal _threshold;

    public MobileAlertObserver(string user, decimal threshold)
        => (_user, _threshold) = (user, threshold);

    public void Update(string symbol, decimal price)
    {
        if (price >= _threshold)
            Console.WriteLine($"  📱 [Mobile] Alert for {_user}: {symbol} hit ₹{price:N0}!");
    }
}

public class EmailAlertObserver : IStockObserver
{
    private readonly string _email;
    public EmailAlertObserver(string email) => _email = email;
    public void Update(string symbol, decimal price)
        => Console.WriteLine($"  ✉️  [Email → {_email}] {symbol} = ₹{price:N0}");
}

public class AuditLogObserver : IStockObserver
{
    public void Update(string symbol, decimal price)
        => Console.WriteLine($"  📋 [Audit] Logged: {symbol} @ ₹{price:N0} at {DateTime.Now:HH:mm:ss}");
}

// ✅ Usage
var market  = new StockMarket();
var mobile  = new MobileAlertObserver("Priya", 1500);
var email   = new EmailAlertObserver("priya@example.com");
var audit   = new AuditLogObserver();

market.Subscribe(mobile); market.Subscribe(email); market.Subscribe(audit);
market.SetPrice("RELIANCE", 1480);
market.SetPrice("RELIANCE", 1520);

market.Unsubscribe(email);
market.SetPrice("RELIANCE", 1550); // Email no longer notified
Subject

StockMarket — holds list of observers, calls Notify on change

Observer

Each alert class — reacts independently to the same event

Loose coupling

Subject doesn't know WHAT observers do — only that they implement Update()

Dynamic

Subscribe/Unsubscribe at runtime — add observers without changing subject

Event-driven Loose coupling Open for new subscribers
C# has this built-in! event keyword + EventHandler delegate IS the Observer pattern. But understanding the manual pattern first makes the built-in version click instantly.
Architectural Pattern

Repository Pattern

Abstracts the data access layer behind an interface. Business logic talks to a repository contract — not directly to the database. Swap SQL ↔ MongoDB without touching your service layer.

Use when: You want to decouple business logic from data access, enable unit testing with mock data, and support multiple data sources cleanly.
Repository Pattern — full product CRUD example
// ✅ Domain model
public class Product
{
    public int     Id       { get; set; }
    public string  Name     { get; set; }
    public decimal Price    { get; set; }
    public int     Stock    { get; set; }
}

// ✅ Generic repository interface — the contract
public interface IRepository<T>
{
    T                GetById(int id);
    IEnumerable<T>   GetAll();
    void             Add(T entity);
    void             Update(T entity);
    void             Delete(int id);
}

// ✅ In-memory implementation (great for testing / prototyping)
public class InMemoryProductRepository : IRepository<Product>
{
    private readonly List<Product> _store = new()
    {
        new() { Id=1, Name="Laptop",  Price=65000m, Stock=10 },
        new() { Id=2, Name="Mouse",   Price=800m,   Stock=50 },
        new() { Id=3, Name="Keyboard",Price=2500m,  Stock=30 },
    };

    public Product GetById(int id)
        => _store.FirstOrDefault(p => p.Id == id);

    public IEnumerable<Product> GetAll() => _store;

    public void Add(Product p)
    {
        p.Id = _store.Max(x => x.Id) + 1;
        _store.Add(p);
        Console.WriteLine($"➕ Added: {p.Name} (ID: {p.Id})");
    }

    public void Update(Product updated)
    {
        var existing = GetById(updated.Id);
        if (existing != null) { existing.Name = updated.Name; existing.Price = updated.Price; }
        Console.WriteLine($"✏️  Updated: {updated.Name}");
    }

    public void Delete(int id)
    {
        var item = GetById(id);
        if (item != null) { _store.Remove(item); Console.WriteLine($"🗑️  Deleted ID: {id}"); }
    }
}

// ✅ Business/Service layer — depends only on IRepository, not the DB!
public class ProductService
{
    private readonly IRepository<Product> _repo;

    public ProductService(IRepository<Product> repo) => _repo = repo;

    public void ShowCatalog()
    {
        Console.WriteLine("\n📦 === Product Catalog ===");
        foreach (var p in _repo.GetAll())
            Console.WriteLine($"  [{p.Id}] {p.Name,-12} ₹{p.Price,8:N0}  Stock: {p.Stock}");
    }

    public void AddProduct(string name, decimal price, int stock)
        => _repo.Add(new Product { Name = name, Price = price, Stock = stock });

    public void ApplyDiscount(int id, decimal pct)
    {
        var p = _repo.GetById(id);
        if (p == null) { Console.WriteLine("Product not found"); return; }
        p.Price = Math.Round(p.Price * (1 - pct / 100), 2);
        _repo.Update(p);
    }
}

// ✅ Wire everything up (in real app, use DI container)
IRepository<Product> repo    = new InMemoryProductRepository();
ProductService         service = new(repo);

service.ShowCatalog();
service.AddProduct("Headphones", 3500m, 20);
service.ApplyDiscount(1, 10); // 10% off Laptop
repo.Delete(2);
service.ShowCatalog();

// To switch to SQL Server: just swap InMemoryProductRepository
// with SqlProductRepository — ProductService doesn't change at all!
Abstraction

IRepository<T> is the contract — business logic only sees this

Implementation

InMemory, SQL, Mongo — each implements the same interface

Testability

Unit test ProductService with InMemory repo — no DB needed

Swap

Change data source by injecting a different repo — zero code changes in service

DB-agnostic Testable business logic Clean separation Works with EF Core
Entity Framework Core already implements Repository-like behavior internally via DbSet<T>. In real projects, add a thin repo layer on top to keep your domain services DB-ignorant and testable.
